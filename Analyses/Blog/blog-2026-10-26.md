# Closed-lid external-monitor power-off: hyprlock exits during FALLBACK transition

An investigation log from a Hyprland session on my laptop: when the only physical monitor was powered off with the lid closed, the lock client died in a very specific Wayland protocol error — and a one-variable environment change stopped it from happening again.

## Setup

Fedora 44; Hyprland `12f242511a9c0fe8a884a9d90511bbbbe044f067`; Aquamarine 0.15.1 (`52ea11f06dd492f34b3cc0b39a9c805beecafcff`); hyprlock 0.9.6 (`e535cf6`); Mesa 26.2.5-1.fc44; Wayland 1.26.0; kernel 7.2.11-200.fc44. This is not a version-matched comparison with the previous desktop.

Hardware: Hybrid AMD + NVIDIA laptop integrated graphics; external DisplayPort monitor (amdgpu-rendered), connector routing confirmed. The exact vendor/model identifiers are intentionally redacted; the terminated client's actual GPU/EGL vendor is unknown. The internal eDP panel is intentionally disabled in this setup. The intended use is **lid closed, external monitor only: powering it off leaves no active physical output**.

## Reproduction

The overnight failure happened with the lid closed and the monitor switched off at its physical power button. A controlled physical power cycle the next afternoon captured the failure:

1. Start hyprlock with the external display active; wait for lock confirmation.
2. Switch the monitor off at its physical power button, then back on (~10 s off).
3. Observe: DP-3 removal → FALLBACK 1920×1080 → hyprlock connection loss and exit 1, before the client logs the monitor's return.

Safety note: the session can remain **locked without a usable unlock UI** (Hyprland stays alive with `locked=true` and an Oops screen). No authentication bypass or destructive recovery is proposed; recovery required a separately authorized session termination and login.

## The failure chain

Anonymized lines (stream order only, not a merged timeline):

```text
client stdout:
  onLockLocked called
  removed iface 72
  output FALLBACK name FALLBACK
  output 73 creating a new lock surface
  Compositor connection was lost, exiting
server stderr:
  unknown object (19), message attach(?oii)
  error in client communication (pid LOCK_CLIENT)
client stderr:
  wl_display#1: error 1: invalid arguments for wl_surface#22.attach
wait result: normal exit_status=1; raw_wait_status=256; signaled=false
```

`19` is the missing **wl_buffer** argument — not output 72/73 and not the receiving surface 22. Its create/import/destroy lifecycle was not captured; the cause remains unknown. In the same server-stderr window, two other client connections also received the same attach-error class; their program identities were not verified. The parallel compositor FALLBACK GBM error was concrete: `eglCreateImageKHR: EGL_BAD_ATTRIBUTE (0x12292): too many plane attributes` on the failing FALLBACK modifier `0x2000000104abb04`. That compositor-side swapchain observation is not proof of this client's buffer-import failure, nor of its temporal precedence. Logind rejected suspend in both incidents; actual system suspend is not established.

## Controls

A roughly twelve-minute lock/authenticate/unlock control with DP-3 remaining connected passed (exit 0). A previous desktop environment reportedly did not exhibit this problem; its exact historical desktop/driver stack was not verified. Neither is an overnight version-matched A/B test for the unmitigated failure.

## The one-variable workaround

In a subsequent 10-hour session with only `AMD_DEBUG=nodcc` added, the same recorded Hyprland and hyprlock versions survived a documented DP-3→FALLBACK→DP-3 cycle. The trigger was full mains power removal from the monitor (verified connector 470 hotplug events, ~5 h 7 min DP-3 absence), closed lid, internal panel disabled. hyprlock survived; the recreated FALLBACK buffer used `0x200000010401b04` (AMD_NO_DCC; the previously failing FALLBACK used a DCC modifier). No `unknown object`/attach- or EGL-import error was recorded; dmabuf-feedback format-table warnings still occurred. One authentication attempt was rejected (wrong password), the same client later authenticated and exited normally. This is a documented observation on this system — **not proof of the root cause.** The workaround is now persistent locally via a session-start wrapper (`AMD_DEBUG=nodcc` before the watchdog and compositor start).

Trade-off: disabling DCC can affect memory bandwidth, power draw and performance on AMD; it also applies to the compositor, not only the lock client.
