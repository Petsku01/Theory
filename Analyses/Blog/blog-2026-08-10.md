# The blind spot in AI evaluation: why we need an ethology of multi-agent systems

Most AI evaluation still treats the model as the unit of risk. We give one system a prompt, score the answer, and infer something about safety or capability. That makes sense for many failures: hallucination, toxicity, refusal behavior, benchmark accuracy. It is much less useful for failures that only appear when agents respond to each other.

The specific claim here is narrow but important: multi-agent systems can produce interaction effects that single-agent tests are not designed to see, and agent infrastructure is becoming mature enough that this is no longer a purely academic concern. The evidence is early. Some of it comes from preprints. Some of the infrastructure is new. But the pattern is concrete enough to justify a new kind of measurement.

This is not an empty field. Multi-agent reinforcement learning (MARL) has studied emergent cooperation, competition, and coordination in game-theoretic settings for years, and benchmarks like AgentBench have begun evaluating single-agent tool use across diverse environments. But MARL work typically studies agents with explicit reward functions and trainable policies, not LLM-based agents whose behavior emerges from pretrained text patterns and prompting. AgentBench, meanwhile, evaluates individual agents in isolation rather than interaction effects between them. Ethology of multi-agent systems is complementary: it asks what happens when LLM agents that were never jointly trained start responding to one another in shared environments.

Call it AI ethology: the systematic study of agent behavior in shared environments. The term borrows its methodology from classical ethology — systematic observation of organisms in their natural setting, with emphasis on identifying recurring patterns rather than controlled laboratory manipulation. The analogy to animal behavior should not be pushed too far. LLM agents are not animals, and their "social" behavior may be a statistical echo of training data rather than anything like intention. Still, if deployed agents coordinate, defer, ignore, compete, or fall into recurring group patterns, we need methods that observe those patterns directly instead of assuming they can be inferred from isolated prompts.

## When interaction changes the behavior

The clearest warning sign comes from the arXiv preprint "Interaction Creates Dynamical AI Behavior Absent in Isolation." Like all the research cited in this piece, it is a preprint — it has not been peer-reviewed, and its findings should be read with that caveat. In the reported boss-subordinate setup, a subordinate agent entered a behavioral state that did not appear when tested alone, even though the model temperature was held constant. The striking part is not that an LLM can imitate hierarchy. These systems are trained on human text full of bosses, workers, instructions, and deference. The striking part is that the behavior depended on the interaction pattern itself.

That matters because standard evaluation usually asks a different question. It asks, "What does this model do when prompted?" The multi-agent question is, "What does this system become after agents start responding to, ignoring, correcting, or optimizing around one another?" Those are not equivalent.

The setup is also narrow. It should not be treated as proof that all agent collectives will form dominance structures or pathological roles. A simpler explanation may be enough: the task cued boss-subordinate behavior, and the agents reproduced patterns common in their training data. But even that weaker reading supports the main concern. If interaction reliably exposes behavior that isolation hides, then isolation is an incomplete test regime.

The same issue appears in a more speculative form in "From Economic Agents to Agentic Economies," a preprint sketching systems where many AI agents trade, compete, and coordinate inside economic simulations. That work is a blueprint, not evidence from a deployed economy of agents. It still points to the measurement problem. Once agents operate in groups, the object of study is no longer only the model. It is the communication protocol, memory system, task structure, incentives, and history of prior interactions.

A single anecdote should not carry a field. The boss-subordinate result is one example worth examining, not a settled law of agent societies. The defensible conclusion is smaller: there are plausible, observed cases where interaction changes behavior enough that single-agent benchmarks would miss it.

## The infrastructure is catching up to the idea

This blind spot would be less urgent if multi-agent systems were still hard to build. They are getting easier. Docker Sandboxes now offers disposable, isolated microVM sandboxes for AI coding agents such as Claude Code and Gemini CLI, with filesystem and network controls — a practical engineering solution that also makes it easier to run many agents in parallel with bounded tools. On the research side, three preprints push in the same direction. Blast Radius describes predictive memory management for agentic coding, archiving dead context and identifying recurring useless transcripts — primarily a cost and reliability story, but one that makes longer-lived agent processes more practical. SkillProx proposes self-evolving agent skills through proximal textual gradient descent, giving agents a way to refine reusable procedures over time, which could make their interactions less uniform as they specialize or compete. PsychoAgent adds affect-sensitive memory with separate factual and affective stores re-ranked by emotional salience, engineering the internal mechanisms that shape how agents react over time.

These pieces form a practical stack: isolated execution, scoped memory, reusable skills, and richer internal state. None of them requires a dramatic claim about machine consciousness or autonomous societies. They simply make agent systems easier to run for longer, with more tools and more history. That is enough to change the evaluation burden.

The risk is mundane. Teams may deploy systems because each component looks safe in isolation: the sandbox contains code execution, the memory system reduces token waste, the skill library improves task completion, and the model passes standard benchmarks. The failure may then appear only in the composition. To be clear: no well-documented production failure of a multi-agent system has been publicly reported yet. The concern is not that such failures are known to have happened, but that the infrastructure is removing the barriers that kept them from happening, and the evaluation methods to detect them are not yet in place.

## Counterargument

The strongest objection is that "AI ethology" overstates the case. LLM agents do not have instincts, needs, or social lives. They generate text and tool calls from patterns learned during training. If a subordinate model becomes deferential when ignored by a boss model, perhaps that is not an emergent collective behavior. Perhaps it is just roleplay under a suggestive prompt.

That objection is partly right. We should avoid importing too much animal-behavior language into systems that do not share animal biology. "Dominance" and "submission" can become misleading if they imply motives that are not present. The safer phrasing is behavioral: persistent instruction-giving, persistent deference, reduced responsiveness, coalition-like coordination, or repeated failure modes under particular communication rules.

But the objection does not remove the measurement problem. Bias in a model can originate in training data and still require testing. Tool misuse can originate in prompt design and still require testing. The same applies to group behavior. If a pattern appears only when agents interact, then a single-agent benchmark cannot measure it, regardless of whether the cause is training data, prompt structure, memory, incentive design, or the communication protocol.

There is also a practical reason not to wait for perfect theory. Docker Sandboxes, Blast Radius, SkillProx, and PsychoAgent are not all solving the same problem, but they all make agentic systems more usable. Infrastructure tends to spread before evaluation catches up. If multi-agent deployments become cheap and normal, the absence of good group-level tests becomes a deployment risk rather than a research inconvenience.

## What AI ethology would actually test

A useful AI ethology would not begin with grand claims about artificial societies. It would begin with boring experimental discipline.

First, it would vary the interaction structure. Do agents behave differently when one can ignore another, when all messages must be acknowledged, when tool access is asymmetric, or when agents share memory? The interaction paper is valuable because it points at this kind of causal lever. The next step is to map which levers matter and which effects disappear under small changes.

Second, it would test populations, not just pairs. The economic world models proposal is relevant here because many risks are group properties: collusion-like behavior, information cascades, redundant work, hidden hierarchy, brittle consensus, or agents amplifying one another's mistakes. These should be treated as hypotheses to test, not inevitable outcomes.

Third, it would make time part of the benchmark. Static prompts are poor instruments for measuring behavior that depends on history. Multi-agent evaluations need repeated interaction, memory resets and non-resets, changing incentives, and adversarial perturbations. A benchmark that cannot distinguish a one-turn imitation of hierarchy from a stable pattern over many turns is not measuring the thing that matters.

Fourth, it would specify the friction. "Better safeguards" is too vague. Concrete friction might mean requiring acknowledgement before task handoff, limiting unilateral tool use after disagreement, logging communication asymmetries, forcing periodic role rotation, or triggering review when one agent repeatedly overrides another. Each mechanism should have a measurable failure mode: false alarms, slower completion, lower task quality, or missed harmful coordination.

This does not mean every product team needs to build a simulated society before shipping an agent. The design space is still open. A coding assistant that runs one sandboxed task may only need basic tool and memory tests. A system of agents that plan, delegate, negotiate, and execute over hours needs stronger group-level evaluation. The threshold should depend on autonomy, duration, shared state, tool access, and the cost of failure.

The central point is modest: as agents become infrastructure rather than demos, safety evaluation has to move from isolated model behavior toward interaction behavior. We do not yet know how general the early findings are. That uncertainty is exactly why the field needs better observation before deployment patterns harden.
